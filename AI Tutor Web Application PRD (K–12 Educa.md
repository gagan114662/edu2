AI Tutor Web Application PRD (K–12 Education)
Overview:
This document outlines a modular feature-branch development strategy for an AI Tutor web application targeting K–12 students. The application provides a Google Meet-style tutoring experience where students engage with a lifelike AI tutor via text and voice in English. The tutor leverages Google’s Gemini Live API for multimodal interactions (text, voice, and potentially screen input/output) and integrates Google OAuth for secure logins. Each major feature is developed on its own Git feature branch, allowing parallel development and CI/CD integration. Major features/branches include user authentication, AI tutoring content generation, real-time voice tutoring, curriculum alignment, student progress tracking, and a parent dashboard. Each feature section below details the branch name, goals, deliverables, tech stack, and acceptance criteria for completion and merge.
Authentication & User Accounts (feature/auth)
Goal:
Establish a secure authentication system so that students (and parents) can log into the AI Tutor platform using Google accounts. This enables personalized sessions and data tracking per user. The goal is a seamless sign-in/up experience (e.g. “Sign in with Google”) that creates or accesses a user profile and ensures only authorized users can access tutoring features. Deliverables:
Google OAuth Login – Implement Google OAuth2 via Firebase Authentication (or Google Identity) for one-click sign-in. This includes a responsive login page with a “Sign in with Google” button.
User Session Management – After login, maintain the user’s session (store auth token or Firebase session) so the user stays logged in across pages. Ensure logout functionality.
User Profile Initialization – On first sign-in, create a new user profile record in the database (e.g. in Firestore) with basic info (unique ID, name, email) and default settings/progress.
Access Control – Protect the main tutor interface so it’s only accessible to authenticated users. If a user is not logged in, redirect to the login page.
(Optional) Parent-Child Linking – Support linking a parent account to a student’s account (e.g. via email or code) if parents will log in separately. This lays groundwork for the Parent Dashboard feature.
Tech Stack & APIs Used:
Firebase Authentication (Google OAuth2 provider) for handling the OAuth flow and token management.
React Firebase SDK on the front-end to trigger Google sign-in and listen to auth state.
Firestore/Database for storing user profiles (if using Firebase) or custom backend API to create user entries upon sign-up.
Node.js/Express (or Firebase Functions) on the backend to verify ID tokens on protected API calls (ensuring only logged-in users invoke tutoring APIs).
Libraries: Firebase JS SDK (for auth), possibly Redux or Context API to store user info client-side, and React Router for navigation control based on auth state.
Acceptance Criteria:
Users can click “Sign in with Google” and successfully authenticate via their Google account. Upon success, the app recognizes the user as logged in (e.g., displays their name or profile).
A new user’s first login creates a database profile entry; returning users retrieve their existing profile (verified via user ID).
Only authenticated users can access the tutoring interface; unauthenticated visitors are redirected to login. Session persists appropriately (e.g., user remains logged in on page refresh until they log out).
The solution uses secure OAuth practices (no exposure of credentials, tokens stored securely). All OAuth integration details are handled by Firebase/Google, simplifying development and security.
Google login works across devices and browsers, and logout functionality properly clears the session. Once this feature is complete and tested (including any UI edge cases and error handling for login failures), the feature/auth branch can be merged into the main branch with all tests passing in CI.
Dynamic Content Generation (feature/ai-content)
Goal:
Implement the AI tutoring brain that generates dynamic educational content and responses. This feature enables the system to understand student queries and produce human-like explanations, answers, or questions in return. The goal is to provide a conversational learning experience where content is tailored to the student’s grade level and context. This branch establishes the core Q&A logic using a large language model, ensuring the tutor can handle a wide range of academic questions and provide helpful, age-appropriate guidance. Deliverables:
LLM Integration (Gemini API) – Connect to the Gemini generative AI API to process text queries and generate text responses. This includes forming API requests with the student’s query (and context) and receiving the AI’s reply. The AI should be configured with a “tutor” persona and any necessary prompt context so its tone and style are appropriate for K–12 students.
Tutoring Logic Module – Create a backend module or service (e.g., an endpoint like /api/askTutor) that orchestrates the query-response cycle. When a student asks a question (text or transcribed speech), this service sends it to the LLM and returns the AI’s answer. Include basic session context management so the AI remembers previous dialogue in a session (for example, using conversation IDs or by sending prior Q&A as context).
Chat UI Component – Develop a front-end component to display the conversation. This includes showing the student’s question and the AI tutor’s answer as chat bubbles or a threaded conversation. If the student inputs text (as an alternative to voice), provide an input box to submit questions. The UI should update in real-time with the AI’s response.
Content Formatting & Safety – Ensure the AI’s responses are presented clearly (supporting basic formatting like math formulas or line breaks if needed). Implement content safeguards: if the AI returns inappropriate or off-topic content, the system should handle or filter it. The Gemini API’s built-in safety settings will be leveraged to enforce child-safe, curriculum-appropriate outputs.
Performance Optimizations – Since this is a core feature, ensure that calls to the AI API are efficient (e.g., using streaming responses if available to show partial answer, or caching earlier context). The deliverable includes handling loading states in the UI (like a “Tutor is thinking…” indicator) to keep the user informed during response generation.
Tech Stack & APIs Used:
Google Gemini API (via Google Cloud Vertex AI or Gemini SDK) for text generation. The model (e.g., Gemini 2.5) will be used to produce human-like answers. The integration may use a REST endpoint or WebSocket for streaming, depending on API capabilities. (Gemini’s Live API supports continuous streaming and real-time responses
ai.google.dev
, but for pure text Q&A, a standard generate call might be used in this branch.)
Backend: Node.js with Express (or Python FastAPI) to implement the /api/askTutor endpoint that forwards queries to the AI. This server holds API keys securely and applies any prompt templates (like adding “You are a kind K-12 tutor…” instructions to each request).
Front-end: React components for the chat interface. State management (using React state or Redux) to store the conversation history.
Libraries: If available, utilize Google’s AI SDK or a library like @google-cloud/ai for easier integration. May also use a utility for markdown or math rendering if the tutor outputs such content (e.g., KaTeX for math formulas).
Prompt Engineering: Not a library, but we will design the prompts and system messages to ensure the AI stays on track (e.g., always responds at an appropriate grade level and in an encouraging tone).
Acceptance Criteria:
When a student asks a question or requests help (via text input or a transcribed voice query), the system returns a relevant, correct, and easy-to-understand explanation or answer. For example, if a student asks “What is photosynthesis?”, the tutor should produce a concise explanation appropriate to the student’s grade, rather than an overly technical paper.
The AI tutor maintains context within a session. If the student asks a follow-up question like “Can you give me an example?”, the tutor’s response references the prior discussion (e.g., continuing the photosynthesis explanation with an example) rather than responding in isolation.
Responses are generated with low latency (for a good user experience, simple questions should be answered within a couple of seconds). The UI should reflect that the system is responding in real-time (showing a loading indicator or streaming text).
All AI-generated content complies with child-safety and appropriateness standards. There should be no profanity, and the content should be factually accurate for the K–12 level. Any factual errors or unsafe outputs from the model are caught and handled (e.g., by the API’s safety filters or an additional validation layer).
The chat interface is intuitive and user-friendly: conversation text is clearly legible, new messages scroll into view, and long answers are wrapped or scrollable. In user testing, students find the AI’s answers helpful and on-topic. Once this feature passes testing (including unit tests for the API integration and UI tests for the chat component), the feature/ai-content branch is merged into main.
Real-Time Voice Tutoring (feature/voice)
Goal:
Enhance the tutoring experience with real-time voice interaction, allowing students to speak to the AI tutor and hear the tutor’s responses. This feature makes the AI tutor feel more natural and engaging, simulating a human tutor who listens and speaks. The goal is to provide a hands-free conversational mode – the student can ask questions aloud and receive immediate spoken explanations – thereby accommodating various learning styles and early learners who may not type easily. Deliverables:
Microphone Input & Speech Recognition – Implement functionality for the student to use their microphone to ask questions. This includes a UI control to start/stop recording (e.g., a “Talk” button or voice icon). Upon activation, the app records the student’s speech and streams it to the AI service for transcription. Voice Activity Detection (VAD) may be used to auto-stop when the student finishes speaking, improving usability.
Streaming AI Response (Voice) – Integrate with Gemini’s Live API to obtain the AI tutor’s response as audio. Rather than waiting for the full text then converting to speech, use streaming so the AI can begin speaking with minimal delay. The tutor’s spoken response should sound natural and clear, creating a conversational flow. (Gemini’s Live API provides low-latency, human-like spoken responses from streamed audio input
ai.google.dev
, ideal for this use case.)
Audio Playback & UI Indicators – Play the AI’s voice response through the web application (e.g., using the Web Audio API or HTML5 audio). Provide visual cues in the UI: for example, show a waveform or subtitles as the tutor speaks, and an indicator when the system is listening vs. speaking. The interface will resemble a video chat: perhaps showing an avatar or tutor image along with voice, and a caption area for the transcribed text.
Error Handling & Fallback – Ensure the system handles cases where voice input isn’t available (e.g., no microphone). In such cases, allow the user to input text as fallback (leveraging the text chat from the previous feature). Also handle API errors or timeouts by informing the user (e.g., “I didn’t catch that, please try again.”).
(Optional) Multimodal Extensions – While primarily focusing on audio, lay the groundwork for future “screen” interactions. For example, the system design will allow incorporating visuals or screen sharing later. (Gemini Live API can process video/screen input in real-time; though not in current scope, the architecture will support adding a whiteboard or image-sharing feature down the line.)
Tech Stack & APIs Used:
Gemini Live API (bidirectional streaming) – Utilized for real-time speech-to-text and text-to-speech with the LLM in the loop. The app will connect via WebSocket to send the student’s audio and receive the AI’s streamed audio response. This ensures low latency, as the AI can start responding before the student finishes speaking in some cases. The Live API’s ability to handle continuous audio streams and return spoken replies creates a natural dialogue experience
ai.google.dev
.
Web Audio/Media APIs – On the front end, use the MediaDevices API to capture microphone audio (e.g., via getUserMedia). Possibly use a library or custom code for encoding audio (to the format expected by Gemini, e.g. 16kHz PCM) and streaming it. For output, use Web Audio API or an <audio> element to play the tutor’s voice stream.
UI Framework – Continue using React for UI. Incorporate a state machine or logic to manage the listening/speaking states. For example, use React state or context to track when the system is recording vs. waiting for a response vs. speaking, to update the UI appropriately.
Real-time Communication – If the front end communicates directly with Gemini’s WebSocket (client-to-server approach), implement token authentication for the API (using ephemeral tokens for security as recommended
ai.google.dev
). Alternatively, use a server proxy (server-to-server approach) if needed for more control. We might leverage third-party integrations like LiveKit or Daily.co which have pre-built solutions for integrating Gemini Live API over WebRTC
ai.google.dev
, to speed up development of reliable streaming.
Voice Settings – Utilize model parameters or TTS settings for voice characteristics. If the Gemini API supports selecting voice profile or language, choose an English voice suitable for children (clear pronunciation, friendly tone). No separate TTS engine is needed since Gemini provides end-to-end speech; however, ensure configuration (like male/female voice, speaking rate) meets user expectations.
Acceptance Criteria:
A student can tap the “Speak” button (or similar) and ask a question verbally; the AI tutor’s response is then heard aloud within a few seconds. For example, the student says “How do I solve this equation?”, and the tutor responds with spoken guidance (e.g., “Let’s work through it step by step…”), without the student needing to read text.
The speech recognition accurately transcribes the student’s question (at least as well as a typical STT system), and the AI’s answer is contextually correct and equivalent to what the text-based system would provide. Transcripts of both the student’s question and the AI’s answer are displayed as text in the chat, so the conversation is also visible.
The end-to-end latency is low enough to feel interactive. Criteria: the AI tutor begins speaking a response within ~2 seconds of the student finishing their question, for a normal-length query. There are no long awkward silences; the conversation flows naturally.
The audio quality of the tutor’s voice is clear and pleasant. The voice has natural intonation and volume. (If using Gemini’s native audio model, it should sound very life-like; if a cascading model, ensure the TTS is high quality.) Users should understand the tutor easily, even without seeing text.
The system can handle a back-and-forth exchange. E.g., the student can ask a follow-up question without reloading the page: the app can listen after finishing a response. No crashes or freezes occur during continuous conversation. If the student speaks over the tutor or starts talking very early, the system either queues their question or politely asks them to wait – it should not break the session.
All relevant edge cases are handled: if the user has no microphone or denies permission, the app detects it and offers a fallback (like using text chat only). If network issues interrupt the voice stream, the app provides feedback (“Connection lost, please try again”) and recovers gracefully. Once these criteria are met in testing (including cross-browser tests for audio features), the feature/voice branch is merged into main.
Curriculum Alignment (feature/curriculum)
Goal:
Align the AI tutor’s content and tutoring plans with official K–12 curriculum standards. This feature ensures that the material the AI covers matches the learning objectives appropriate for the student’s grade, school syllabus, or education standards (e.g., Common Core, state standards, or specific curricula like Cambridge or Ontario). By doing so, the AI tutor will reinforce what students are learning in school and fill gaps without going off-topic or beyond scope. It basically acts as a curriculum filter and guide, so the AI’s dynamic content is always relevant to the student’s required learning path
curioused.ai
. Deliverables:
Curriculum Data Model – Define a structured representation of the curriculum. For example, create a Firestore collection or JSON dataset of subjects -> grades -> topics -> subtopics/standards. Each item can have metadata like standard ID (e.g., “CCSS.MATH.5.NBT.A.1”), description, and maybe prerequisite relationships. This serves as the knowledge map the tutor should follow.
Profile Settings for Curriculum – Extend the user profile to include curriculum settings, such as the student’s grade level and curriculum framework (e.g., “Grade 5 – Common Core Math & English”). This allows the system to know which set of standards or topics to prioritize for that user. Possibly provide a UI dropdown during onboarding for the student/parent to select their curriculum or school system.
AI Prompt Enhancement – Modify the AI tutoring logic to incorporate curriculum alignment. For instance, when generating content, the system will inject the relevant topic or standard into the AI’s prompt or function calls. If a student simply asks a general question, the system can infer which curriculum topic it relates to and guide the answer accordingly. If the student is practicing a specific skill, ensure the AI stays within the boundaries of that skill’s definition. (In practice, this could mean using the curriculum map to fetch context or examples for the AI, or to politely steer unrelated questions back to the curriculum scope.)
Curriculum Progress Mapping – As the student learns, tag their progress against the curriculum. The feature will include logic to mark curriculum topics as “covered” or learning objectives as “mastered” when the AI determines the student has demonstrated understanding (in conjunction with the Progress Tracking feature). Deliverables include a way to record which curriculum items have been addressed in tutoring sessions.
Curriculum Browser UI – (Optional/nice-to-have) Provide a UI component that lets students (or parents) see the curriculum outline and choose or review topics. For example, a “Curriculum” tab where the student can pick a topic they want help with (the tutor session will then focus on that topic), or see which areas are completed. This makes the learning process transparent and user-driven when needed (similar to an “All Topics Menu” that allows access to any syllabus topic
curioused.ai
).
Tech Stack & APIs Used:
Database: Use Firestore (or a JSON file) to store curriculum information. This data might be loaded into memory or queried as needed. It could include tables/collections like CurriculumStandards and UserCoverage.
Backend Logic: Extend the tutoring backend service to utilize curriculum data. For example, implement a function like getRelevantStandard(query, userGrade) that can identify which curriculum standard a question relates to (via keyword matching or a simple classification). Alternatively, maintain an explicit context: if the user chose a topic to practice, attach that to the session context so the AI knows to stick to it.
Integration with LLM: The Gemini API calls may include few-shot examples or instructions drawn from curriculum resources. If available, integrate an API or library of open educational content (for example, Khan Academy exercises or Common Core examples) to supplement the AI’s responses with curriculum-aligned examples. (If no external API, we rely on the LLM’s knowledge, but possibly constrain it with system messages about the curriculum).
Frontend: React components for any curriculum selection or display. Possibly a tree view or list of topics by grade. Could use a UI library for tree controls or accordions to show the syllabus outline. Also, badges or progress indicators next to each topic could show completion status (once integrated with progress tracking).
APIs/Standards: There may not be a ready-made public API for curriculum standards (some vendors exist, but we can hardcode or manually input data for now). This feature might involve research into the relevant standards (e.g., Common Core standard IDs, etc.) to populate our alignment dataset.
Acceptance Criteria:
The system successfully tailors its content to the defined curriculum for the user. For example, a 5th-grade student in the system should predominantly receive material from the 5th-grade curriculum. If they try to veer into an unrelated or more advanced topic, the tutor gently redirects or simplifies the content to match their level.
When the student requests help on a specific topic (whether explicitly via a curriculum browser UI or implicitly via their question), the AI’s answers align with the correct standard. Acceptance test: Suppose a student profile is set to “Grade 4 Math – Common Core” and they ask, “How do I multiply two-digit numbers?” The AI’s response should cover the standard method for multi-digit multiplication appropriate for 4th grade (and possibly mention it’s a Grade 4 skill), rather than using techniques too advanced or not in the curriculum.
Every tutoring session or Q&A can be tagged with the relevant curriculum topic/standard. This criterion is met if, for instance, after a session, the system can record that “Standard XYZ was practiced.” In practice, this might be verified by inspecting logs or the progress database – it shows entries linking the session to curriculum identifiers.
The user can see or select curriculum topics in the UI (if that deliverable is implemented). For instance, a student could open a “Topics” list and click on “Fractions” under Grade 3 Math, and the tutor will then focus on that topic. The acceptance is that the system indeed then guides the session around fractions and doesn’t stray to unrelated content.
No curriculum misalignment: the tutor should not provide content that is clearly outside the scope of the chosen curriculum. This can be tested by providing queries that might tempt the AI to go off-track. For example, a student in Grade 5 asks about “calculus”; the expected behavior is the tutor might say “Calculus is beyond your level, let’s focus on something else” or give a very high-level answer, rather than diving into college-level detail.
This feature is considered done when tests show the AI’s output is consistently on-curriculum for various scenarios, and the development team has a way to adjust or update the curriculum data as needed. After code review and passing integration tests (ensuring this branch doesn’t break existing voice or content functionality), the feature/curriculum branch is merged.
Student Progress Tracking (feature/progress)
Goal:
Implement comprehensive tracking of student performance and activity over time. The purpose of this feature is to record what the student has done and how they are improving, enabling personalized learning and providing feedback to the student (and stakeholders). The system will log key metrics such as topics covered, proficiency levels, time spent, and improvement areas. Ultimately, progress tracking allows the AI tutor to adapt to the student’s needs (by focusing on weaker areas) and provides students with a sense of accomplishment as they see their growth. Deliverables:
Progress Data Schema – Design a data model to store progress information. For example, a Firestore collection UserProgress where each document corresponds to a student and contains fields like: total sessions, total time spent, list of topics practiced with counts or mastery levels, recent scores or performance metrics, and timestamps of last activity. If using a relational model, define tables for user, session logs, and skill mastery.
Logging Mechanism – Build functionality in the backend to log relevant events to the progress store. This includes: when a tutoring session starts and ends (for time tracking), what curriculum topic or standard was covered, and any assessment of performance. For instance, if the tutor asked the student a practice question and the student answered (perhaps via voice), log whether it was correct. The deliverable could be implemented as middleware or hooks in the Q&A flow – after each question/answer exchange, update the progress records accordingly.
Progress Analysis – Implement basic analytics to interpret the raw logs into meaningful progress measures. For example, calculate a mastery score per topic (perhaps using a simple algorithm: each time the student answers a question correctly on a topic, increase their score; if they struggle, note that). This can be done on the fly or with cloud functions that aggregate data periodically.
Student Progress UI – Create a front-end dashboard or component accessible to the student that displays their progress. This should be user-friendly and motivating. Key elements might include: a progress summary (e.g., “You have completed 5 sessions, practicing 3 different topics”), visual indicators like a progress bar for each subject or a chart showing improvement over time, and perhaps badges or achievements (e.g., “Fraction Master – completed 10 fraction problems!”). The UI should update as new data comes in (maybe fetch fresh data at session end or use real-time listeners if using Firestore).
Data Privacy & Security – (Implicit deliverable) Ensure that progress data is only accessible to authorized users. This means implementing security rules (if using Firebase) or backend checks so that one student cannot read another’s progress. This also ties into the Parent Dashboard where parents can view their child’s data – that linking must be secure.
Tech Stack & APIs Used:
Database: Firebase Firestore will serve as the primary store for progress data. It offers real-time updates (if we choose to use snapshot listeners to update the UI live) and integration with Firebase Auth for security rules (e.g., only allow read/write on /UserProgress/{userId} if userId == auth.uid or if the auth user is a linked parent).
Backend: Node/Express or Firebase Cloud Functions to handle writing to progress logs. For example, when the tutoring service completes an answer, a function could trigger to record the event. If complex calculations are needed (like updating mastery levels), a Cloud Function can run in the background on certain triggers (e.g., every time a session ends, recompute some summary stats).
Front-end: React components for the dashboard. Possibly integrate a chart library (such as Chart.js or Recharts) to visualize progress data (like a line chart of performance or a pie chart of topics covered). Use context or global state to store progress info fetched from the backend so it can be displayed across the app (for instance, a sidebar widget showing overall progress).
Time Tracking: Use JavaScript timers or backend timestamps to record session durations. Could also integrate with the browser’s Page Visibility API or similar to detect if the student is active, but a simpler approach is to measure from session start to end.
Analytics Standards (Optional): Internally, data can be structured to align with standards like xAPI (Experience API) which logs learning experiences (e.g., “Student X answered question Y with result Z” events)
getmagicbox.com
. While we may not fully implement an xAPI LRS, being mindful of these standards can help if we later integrate with other learning systems.
Acceptance Criteria:
The system reliably records progress data for each relevant student action. For example: when a student completes a tutoring session on “Decimals,” the database entry for that student should reflect an update such as incrementing the count of problems done in the “Decimals” topic and recording the date/time. This can be tested by running a session in a dev environment and then checking the Firestore data for correctness.
A student can view their progress dashboard and it accurately reflects their activity. For instance, if a student has practiced 5 topics, the dashboard should list those 5 topics and possibly a completion or mastery level for each. If they spent ~30 minutes total in sessions, that should be indicated. The data on the UI should match what’s in the database for that user.
Progress visualization is clear and encouraging. During user testing, students should be able to interpret the dashboard (e.g., “I see I’m 80% done with Grade 4 Math curriculum” or “I’ve improved in Reading this week”). An acceptance criterion is qualitative: the progress UI should follow UX best practices (short paragraphs of feedback, use of icons or colors to highlight progress) and be free of clutter.
The system can distinguish different levels of proficiency. For example, if the student consistently answers a certain type of question correctly, the system might mark that skill as “mastered.” Conversely, areas where the student struggles might be flagged. The acceptance is that this logic correctly identifies at least basic cases (not expecting complex AI evaluation, just rule-based is fine initially).
Security test: One user cannot see or alter another user’s progress via direct API calls or front-end (except via authorized parent access). We consider it accepted when, for example, trying to manually query another user’s progress data (by modifying the request) is denied by the security rules or backend checks.
All progress-related functionality should not significantly degrade performance. Even as the log grows, queries for the dashboard should be efficient (using indexed fields or batched aggregation if necessary). Once the feature is unit and integration tested (including simulation of multiple sessions and verifying data integrity), the feature/progress branch is approved for merge.
Parent Dashboard (feature/parent-dashboard)
Goal:
Provide parents/guardians with a dedicated dashboard to monitor and support their child’s learning progress. This feature aims to foster active parent participation in the student’s studies by giving a clear overview of the child’s activities and achievements in the AI tutor platform
getmagicbox.com
. Parents can use this dashboard to understand what their child is learning, track improvement over time, and ensure the tutoring aligns with their expectations. It strengthens trust in the platform and encourages a home-school connection by keeping parents informed. Deliverables:
Parent Login/Access Control – Ensure that a parent can log in (likely using the same Google OAuth system) and be identified as a parent user. This may involve a simple role attribute in the user’s profile (e.g., role: 'parent') or a separate parent account creation flow. The system must link parent accounts to one or more student accounts (for instance, by email association or an invite code, as set up in the Auth feature). This linking mechanism is a critical deliverable so the dashboard knows whose data to show.
Dashboard Overview Page – Develop the main parent dashboard UI, accessible after parent login. This page should summarize the child’s key metrics: total tutoring time this week/month, number of sessions completed, overall progress through the curriculum, and perhaps the child’s current strengths and weaknesses. For readability, use cards or sections for each type of info (e.g., “Engagement: 5 sessions this week”, “Subjects Practiced: Math, Science”, “Mastery: 70% of Grade 5 Math completed”).
Detailed Reports – Provide the ability for parents to drill down into more detailed reports. For example:
Progress by Topic/Subject: a section where the parent can see each subject (Math, English, etc.) and the child’s progress or proficiency in each, possibly represented by percentage of curriculum completed or a skill rating.
Recent Activity Log: a timeline or list of recent tutor sessions or questions asked, with timestamps and outcomes. (E.g., “June 18: 30 min session on Fractions – Completed 5 practice questions, Accuracy: 80%”).
Performance Trends: a simple chart showing improvement or activity over time (e.g., weekly hours spent or assessment scores over time if applicable).
Notifications/Alerts – (Optional) A system to highlight important information for the parent. For instance, an alert if the child hasn’t practiced in a while (“John hasn’t had a session in 5 days”) or if the child mastered a new topic (“John mastered Multiplication!”). These can be shown on the dashboard as highlighted messages. This is not a strict requirement for MVP, but a nice addition if time permits.
Export/Sharing Options – (Optional) Allow parents to export progress reports (e.g., PDF summary of the month’s activity) or share them with teachers. This could be a simple “Download Report” button on the dashboard which formats the key data into a PDF. While not core, it is useful for integrating with real-world parent needs (similar to how some platforms let you export progress data for parent-teacher meetings).
Tech Stack & APIs Used:
Front-end: Use React to build the dashboard pages. Many components can reuse those from the student progress UI (for example, the charts or progress bars). We might leverage a component library for admin dashboards (to get pre-styled charts or card layouts). For charts, again Chart.js or similar can be used to visualize data (like a line graph of weekly performance).
State Management: Upon parent login, the app needs to fetch the child’s data. If one parent account is linked to multiple children, include a selector UI (e.g., a dropdown to switch between Child A and Child B). Use React state or context to store the currently selected child’s progress data for display.
Backend: Provide an API endpoint (or Firestore query) that given a parent’s user ID, returns the relevant child’s progress info. This might be a custom cloud function that verifies the parent-child link and aggregates data (e.g., GET /api/childProgress?parentId=X returns a summary). If the data volume is small, the client can directly read the child’s progress document(s) from Firestore (with security rules allowing it only if linked).
Linking Mechanism: Use the approach defined in Auth – for example, when a student signs up, they (or the admin) can add a parent email to their profile. Then when that parent signs in, the backend knows which student’s data to fetch by matching emails. Alternatively, use a code/invite system for higher security. The exact method should be implemented and tested.
No Additional AI: The parent dashboard mostly displays stored data, so it doesn’t heavily use the AI APIs. However, we could optionally use the LLM to generate a short natural-language summary for the parent (“John is doing great in math but should spend more time on reading comprehension.”). If we do this, we’d call the Gemini API with a prompt summarizing the progress data. This is an enhancement, but not required.
APIs/Libraries: Utilize any needed library for PDF generation if export is implemented. Also use date libraries (like date-fns or Moment.js) to nicely format dates (e.g., “Jun 20, 2025”) in logs.
Acceptance Criteria:
A parent user (with a linked child) can log in and is presented with a dashboard containing their child’s data. The dashboard loads without manual input of student ID (i.e., the system automatically knows which child(ren) to show based on the parent’s account link).
The information shown on the dashboard is accurate and up-to-date. If the child completes a tutoring session, the parent dashboard reflects the new progress (either immediately or upon next login). For example, if a child just mastered a new topic, the parent’s view should show that topic as mastered.
